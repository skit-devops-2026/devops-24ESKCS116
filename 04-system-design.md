# 04 — System Design

## 1. Design principle

Use the course syllabus stack and the least complicated architecture that meets the acceptance criteria. Preserve the current frontend before making structural changes. Avoid adding libraries unless a clear requirement justifies them.

## 2. Recommended technology stack

| Layer | Choice | Why |
|---|---|---|
| Markup | HTML / JSX | Existing markup can be reused where appropriate |
| Styling | Existing CSS; Tailwind only if already configured and useful | Preserves design and avoids unnecessary rewrite |
| Frontend | React | Reusable components and state-driven UI |
| Client routing | React Router, if the app needs multiple client routes | Demonstrates SPA routing |
| HTTP requests | Browser `fetch()` | Directly understandable client-server communication |
| Runtime | Node.js | Backend JavaScript runtime |
| Server | Express.js | Simple REST API and middleware |
| Database | MongoDB | Matches syllabus |
| Data modeling | Mongoose | Schemas, validation, and database operations |
| Password hashing | `bcrypt` or `bcryptjs` | Never store plain-text passwords |
| Authentication | JWT or session-based approach, selected after source inspection | Protects user-specific routes/data |
| Development config | `.env` | Keeps credentials out of source code |

Avoid adding Next.js, TypeScript, Supabase, Drizzle, Redux, Zustand, TanStack Query, Recharts, Framer Motion, shadcn/ui, or a drag-and-drop library unless the ZIP reveals that a tool is already configured and keeping it is safer than removing it.

## 3. Database decision

**Current status: undecided. Recommended default: MongoDB Atlas** if an account and internet connection are available, because it avoids installing and maintaining a local database. If MongoDB is already installed and working locally, local MongoDB may be faster.

Keep the database connection behind one environment variable such as `MONGODB_URI`, so the application code does not depend on whether the database is local or hosted.

Do not commit the real URI or password. Provide `.env.example` with placeholder values only.

## 4. High-level architecture

```text
Browser
  |
  | React UI + existing CSS
  | fetch() sends HTTP requests
  v
Express REST API (Node.js)
  |
  | authentication middleware
  | route validation and ownership checks
  v
Mongoose models
  |
  v
MongoDB
```

**Request example — creating a task:**
1. User fills in the task form.
2. React validates basic required fields.
3. `fetch()` sends a POST request to the Express API.
4. Authentication middleware identifies the user.
5. The route validates the project and checks that the user owns it.
6. Mongoose saves the task in MongoDB.
7. The API returns the saved task as JSON.
8. React updates the displayed task list.

## 6. Data model

### User
- `name`: string, required.
- `email`: string, required, unique, normalized to lowercase.
- `passwordHash`: string, required; generated by password hashing.
- timestamps: created/updated dates.

Never return `passwordHash` in API responses.

### Project
- `name`: string, required.
- `description`: string, optional.
- `owner`: reference to `User`, required.
- timestamps.

### Task
- `title`: string, required.
- `description`: string, optional.
- `status`: enum `To Do`, `In Progress`, `Done`; default `To Do`.
- `priority`: enum `Low`, `Medium`, `High`; default `Medium`.
- `project`: reference to `Project`, required.
- `owner`: reference to `User`, required (useful for explicit ownership checks).
- timestamps.

A separate Workspace, Sprint, Stage, Comment, Attachment, Notification, or Membership model is not needed for the minimum version.

## 7. API and ownership rules

- API routes should return JSON and meaningful HTTP status codes.
- Authentication middleware must verify the current user before protected operations.
- Every project query must be scoped to the current user.
- Before reading/updating/deleting a task, verify that its project belongs to the current user (and/or validate its owner field consistently).
- Do not rely on hiding buttons in React for security.
- Validate IDs, required fields, status values, and priority values on the server.
- Handle database connection failure and unexpected route errors without exposing secrets.

## 8. Authentication recommendation

Implement only email/password signup, login, and logout for this deadline. Do not add OAuth, magic links, or password reset unless the required flow is already present and working.

- Hash passwords using `bcrypt`/`bcryptjs`.
- Verify passwords during login.
- Protect the API with middleware.
- Keep the token/session secret in an environment variable.
- If JWT is selected, do not hard-code the signing secret. Token transport and expiry must be documented in the actual implementation.
- Return only safe user fields such as ID, name, and email.

The exact token transport should be chosen after source inspection, balancing simplicity, security, and compatibility with the existing frontend.

## 9. Error handling

- Use `400` for invalid request data.
- Use `401` for unauthenticated requests.
- Use `404` when a resource is absent or inaccessible to the current user.
- Use `409` for duplicate email.
- Use `500` for unexpected server failures.
- Frontend should display a human-readable message and should not assume every request succeeds.

## 10. Configuration

Expected environment variables may include:

```text
PORT=5000
MONGODB_URI=your_mongodb_connection_string
JWT_SECRET=replace_with_a_long_random_secret
```

Use only the variables needed by the selected implementation. `.env.example` contains placeholders; the real `.env` must stay local and must not be included in the ZIP or committed to Git.

## 11. Security and limitations

This is an academic demonstration, not a production SaaS. It must still hash passwords, protect routes, validate requests, enforce ownership, and keep secrets out of source control. Do not claim production-grade security, multi-user collaboration, or features that are not actually implemented.
